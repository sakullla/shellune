## 2. Windows 11 x86_64：实际运行了什么

### 2.1 环境

- 操作系统：Windows 11，build `10.0.26300.9711`（注册表 `DisplayVersion` = 26H2；
  `ProductName` 仍是系统自带的旧字符串 “Windows 10 Pro”，不是发行版名称）。
- 版本类型：Professional，x86_64 / AMD64。
- CPU：Intel Core i7-9700F @ 3.00 GHz。
- 显示：3840×2160，缩放 150%（144 DPI），DWM 合成；GPUI 0.2.2 的 DirectX 渲染后端。
- 工具链：rustc 1.99.1 (58cf8f9c3 2026-10-13)，edition 2024；OpenSSH for Windows
  （`ssh.exe` 来自 `C:\WINDOWS\System32\OpenSSH`）；WSL2 Debian（SSH 集成测试用）。
- 桌面环境：Windows 原生桌面（无第三方窗口管理器）。

### 2.2 构建与产物

交付命令（与计划里的 `delivery_verification.full` 相同）：

```sh
cargo fmt --all -- --check && cargo clippy --workspace --all-targets --all-features -- -D warnings \
  && cargo test --workspace --all-features -- --include-ignored && cargo build --workspace --release
```

- 结果：见第 5 节的输出摘要。
- 发布产物：`packaging/windows/make-portable.py` 生成的便携包
  `dist/Shellune-0.1.0-windows-x86_64-portable.zip`，内含 `shellune.exe`、
  `LICENSE`、`README.txt`。
- 大小与校验和：zip 6,975,431 字节（约 6.7 MiB），其中 shellune.exe 18,023,936 字节；
  SHA-256 = 7ebe2371bcd01d24ade189245d7b6e1af659814dd6b8c9e7e7833d6f0c39928a（同目录 .sha256 文件）。
- 签名状态：**未签名**。本项目没有代码签名证书；Windows SmartScreen 会提示未知发布者。
- 该 zip 里的 `shellune.exe` 被解压后实际启动过（见 2.3），不是只打包未运行。
- NSIS 安装包：`packaging/windows/shellune.nsi` 已写好，但本机没有 NSIS，**未编译**，

### 2.3 启动

- 启动方式：直接运行 release 构建的 `shellune.exe`（以及便携包内同一文件）。
- 观测：窗口标题 `Shellune`，客户区 `1680×1080 物理像素`，窗口 DPI `144`，
  即 1120×720 逻辑像素，等于 `DEFAULT_WINDOW_SIZE`；stderr 为空。

### 2.4 验收操作：做过什么、没做什么

在运行中的应用里用真实鼠标与键盘事件驱动，并用文件副作用核对结果：

| 需求 | 操作 | 观测事实 |
| --- | --- | --- |
| R1 | 启动 release 产物与便携包内产物 | 窗口出现，客户区 1680×1080 物理像素 / DPI 144 |
| R2 | 新建本地终端，执行 `cd C:\Users; pwd`、`echo ... > 文件` | 输出与本机执行一致，文件被真实写出 |
| R8（中文） | 在终端键入 `echo 中文输入测试 > r8-zh.txt` | 文件内容为 `中文输入测试`（UTF-16LE） |
| R8（尺寸） | 窗口 1680×1080 → 1350×900 → 复原 | Shell 内 `$Host.UI.RawUI.WindowSize`：95×21 → 66×12 → 95×21 |
| R8（持续输出中断） | 前台运行 ping / 脚本循环后按 Ctrl+C | **未中断**：界面持续变化 28,396 → 23,983 像素/秒，提示符未恢复 |
| R8（交互式程序） | 在本地终端启动 MSYS Vim 并尝试编辑 | **未取得可信结果**：无法在无辅助功能树的环境里校对全屏渲染 |
| R12 / R13 | Ctrl+1…4、Ctrl+L、Ctrl+= 与文字大小控件 | 每次操作都有可测的整屏重绘（115,139 / 22,650 / 162,257 / 213,968 像素） |
| R3—R7、R9—R11 | 未在运行窗口内逐项操作 | 证据来自自动化测试（第 5 节），**不是**本次运行窗口的证据 |
| R4（系统 Agent） | 尝试启动 Windows OpenSSH 认证代理服务 | `sc start ssh-agent` 返回 1058（服务被禁用，需管理员提权），`ssh-add -l` 无可用 Agent；Pageant 未安装。**未验证** |

为什么 R3—R11 没有在运行窗口里逐项操作：本环境没有辅助功能树（gpui 0.2.2 没有
AccessKit），代理也无法读取屏幕文本，只有像素与文件副作用可用；SSH/SFTP 表单需要逐
字段点击输入，无法可靠判定每一步的界面反馈。因此这些流程的证据是第 5 节的自动化测试
（其中 SSH/SFTP 用例驱动真实的 OpenSSH 服务器），而不是在窗口里点过。这一点必须按
未验证对待，不能写成已通过。

## 7. 本轮发现、未解决的缺陷

### 7.1 Windows：Ctrl+C 不能中断正在运行的命令（R8 未满足）

复现：本地终端里运行 `ping -n 20 127.0.0.1`（或 `cmd /c ping -n 20 127.0.0.1`），
3 秒后按 Ctrl+C。界面持续变化（28,396 → 23,983 像素/秒），提示符不回来。

对照与定位：

- 同一台机器的 Windows Terminal 里跑同一命令，Ctrl+C 后 3 秒内提示符恢复。
- 字节级追踪（临时 eprintln，已回退）显示应用处理了按键并写出 `0x03`：
  `key "c" ctrl=true` → `write [3]`；`Ctrl+A`、`Tab`、`Up` 也都写出了对应字节。
- 同一台机器上手写的 `portable-pty` 最小复现程序向 `cmd /c ping` 写 `0x03` 能中断它。

结论：编码与写入没有丢字节，问题在 ConPTY 把 `0x03` 转成控制事件这一步在 PowerShell
前台时没有发生。下一步候选修复是按键为 Ctrl+C 时额外投递一次控制台控制事件
（`AttachConsole` + `GenerateConsoleCtrlEvent`），但它会牵动应用自身的控制台，
本轮没有冒险改动，也没有把结论改成已验证。

### 7.2 其他残余

- 真实中文输入法（候选窗与组合过程）没有驱动过，只验证了 Unicode 字符提交与显示。
- Windows 上未能在运行窗口里逐项走 R3—R11 的 SSH/SFTP 流程（原因见 2.4）。
- 没有应用图标；macOS/Linux 的打包脚本从未执行。

## 8. R14—R17 边界复核

产品、文档与打包文本一致声明：无终端分屏、无跳板机/ProxyJump 管理、无端口转发管理、
无断点续传。`docs/release/0.1.0-release-notes.md`、打包 README、
`docs/design/02-shell-and-design-system.md` 均未把这些写成功能；SSH 配置导入遇到
`ProxyJump`/`ProxyCommand`/转发指令时只给出限制提示（自动化测试覆盖）。
