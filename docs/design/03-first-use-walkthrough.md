# 首轮任务走查记录（T2）

走查对象：本任务交付的 GPUI 外壳。走查目标（R12、R13）：确认用户能找到四类对象的入口、
能辨认当前对象与状态、失败与缺失不会伪装成成功，并记录造成误解或需要反复寻找的环节；发现
的问题在本任务内修正或如实留下。

## 1. 环境

- Windows 11，x86_64，Console 会话 2，显示缩放 150%（DPI 144）。
- 构建：`cargo build`（debug），运行 `shellune.exe`；窗口标题 `Shellune`，默认请求
  1120×720，最小 720×480（`src/app/mod.rs`）。
- 自动化：`cargo test` 中的 GPUI 测试把真实 `ShelluneView` 挂载到测试窗口，读取元素实际布局框
  （`VisualTestContext::debug_bounds`）并注入点击与按键。

## 2. 走查步骤与结论

| 步骤 | 走的路径 | 结论 |
| --- | --- | --- |
| 首次打开 | 启动应用，看第一帧 | 四个入口在导航中一次可见，标题行说明"当前对象" |
| 分区切换（鼠标） | 点击导航第 2 项 | 对象区切换，窗口重绘约 4.9 万像素差异 |
| 分区切换（键盘） | Ctrl+2 / Ctrl+3 / Ctrl+4 | 每次切换都有约 4.8—8.4 万像素变化，与鼠标结果一致 |
| 语言切换 | Ctrl+L | 文案整体切换（约 3.2 万像素变化），产品名与英文简介保持不变 |
| 文字大小 | Ctrl+= | 度量整体放大（约 20 万像素变化），导航仍在窗口内 |
| 主按钮（能力缺失） | 点击"新建本地终端" | 只出现提示条，不产生任何对象（由 GPUI 测试断言） |
| 最小窗口 | 720×480 下重新布局 | 四个导航入口、标题、主按钮、状态卡片全部在窗口内 |
| 最大字号 + 最小窗口 | 115% + 720×480 | 无越界、无遮挡（由布局测试断言） |

## 3. 发现与处理

### F1 选中项只靠背景色区分（已修正）

导航选中态原先只有 `#1e2431` 与 `#12151c` 的差异（对比度约 1.9:1），而强调色 token 在整个
首帧里一次都没出现。"当前对象"因此在配色上并不突出。

处理：为选中项增加 2px 强调色竖条（`view.rs` 的导航行），非选中项用行背景色绘制，切换时
不发生位移。修正后首帧出现强调色像素（约 68 个），并且强调色对选中背景的对比度为 7.7:1。

### F2 快捷键在首帧不可用（已修正）

写按键测试时发现：没有任何元素持有焦点时，动作不会被派发；应用若等到用户点击才建立焦点，
Ctrl+1…4 在首帧就是死键。

处理：窗口创建后立即把焦点交给外壳根节点（`open_main_window` 中的 `window.focus`），
测试也用同样的前置条件派发动作。

### F3 "放大"实际上会变小（已修正）

最初的动作名与语义是"增大字号"，但三档循环走到 115% 之后会回到 90%，第二次点击会让文字变
小，与名称矛盾。

处理：改为单一"文字大小"控件（`CycleTextSize`），导航栏底部同时显示当前百分比，标签与行为
一致。

### F4 失败会话缺少原因（已修正）

会话行原先只显示"类型 · 状态"，一个断开的会话看不出是超时、拒绝还是认证失败。

处理：断开与失败状态改为显示传输层给出的原因（`SessionFailure` 的 Display 文本，本身不含
秘密）；其余状态仍显示本地化状态标签。

### F5 150% 显示下首帧偏小（T11 复核后认定该结论错误，见第 6 节）

实测：请求 1120×720，窗口客户区为 1120×720 **物理**像素，在 150% 缩放下相当于 746×480 逻辑
像素，正好落在最小尺寸附近。gpui 0.2.2 的 Windows 后端把传入的 bounds 当作物理像素
（`platform/windows/window.rs` 中 `physical_size.to_pixels(scale_factor)`），因此首帧比设计
假设更紧凑。

当前判断与证据：

- 布局在 746×480 逻辑像素下仍然完整（720×480 的最小窗口测试覆盖同一场景，无越界、无遮挡）。
- 尝试过在窗口创建后按逻辑尺寸调用 `window.resize` 进行纠正；实测客户区尺寸没有变化
  （仍为 1120×720 物理像素），属于无效修改，已回退，没有留在代码里冒充修复。
- 该问题涉及三端 DPI 与真实图形环境，按计划属于 T11 的三端视觉评审范围，本文件保留实测数值
  与不修正的理由，不声称已解决。

### F6 走查证据形式的限制（如实记录）

本环境的屏幕捕获会把窗口上方的桌面内容一起抓进来，无法据此声称精确的像素几何。因此：

- 几何结论一律来自 GPUI 测试读取的布局框（导航、标题、主按钮、状态卡片、行）。
- 像素统计只用于两类判断：主题是否真的生效（画布 / 面板 / 强调 / 状态色都出现且比例合理），
  以及交互是否改变了界面（按键与鼠标操作后的差异像素数）。

## 4. 本次验证统计

- `cargo test`：25 项通过（10 项 GPUI 布局与交互，12 项模型与文案，3 项配色对比度）。
- `cargo clippy --workspace --all-targets --all-features -- -D warnings`：通过。
- `cargo fmt --all -- --check`：通过。
- 运行验证：应用在 Windows 11 / 150% 缩放下启动、接受键鼠输入、退出码与 stderr 为空（超时方式
  结束）。

## 6. T11 三端复核：Windows 11 实测（2026-11-06）

本节是 T11 对上述走查的复核：同一台机器、同一套界面，但用运行时坐标与像素统计重新
测量，并记录本轮发现的问题。macOS 与 Linux 仍未运行（见本节末与
`docs/release/0.1.0-verification.md`）。

### 6.1 环境

- Windows 11 build 10.0.26300.9711（注册表 `DisplayVersion` 为 26H2；
  `ProductName` 仍是系统自带的旧字符串 Windows 10 Pro），Professional，
  x86_64 / AMD64，Intel Core i7-9700F。
- 显示器 3840×2160，缩放 150%（144 DPI），DWM 合成，gpui 0.2.2 的 DirectX 渲染后端。
- 运行对象：`cargo build --workspace --release` 产出、再由
  `packaging/windows/make-portable.py` 打进便携包的
  `shellune.exe`（release 构建，不是 debug 构建）。

### 6.2 F5 的结论被推翻

用 `GetClientRect` + `ClientToScreen` 在 DPI 感知的进程里测量运行中的窗口：
客户区 **1680×1080 物理像素**，窗口 DPI 144（150%），也就是 **1120×720 逻辑像素**，
正好等于 `DEFAULT_WINDOW_SIZE`。

gpui 0.2.2 的 Windows 后端在创建窗口时会把逻辑 bounds 换成设备像素
（`platform/windows/window.rs` 的 `handle_new_window` 里
`bounds.to_device_pixels(scale_factor)`），所以首帧不是"1120 物理像素"，而是设计的
1120×720 逻辑像素。T2 记下的"客户区 1120×720 物理像素"是测量方式的产物：在 150%
缩放下，未声明 DPI 感知的查询与截图给出的是虚拟化后的数值，不能当作布局尺寸。

结论：这里没有需要修的 DPI 缺陷，需要改的是测量方法。本节取代 F5 的判断，F5 的
"未修正"标记保留下来只作历史记录。

### 6.3 本轮实测（数值是两次抓帧之间的差异像素，物理像素）

| 动作 | 观测 |
| --- | --- |
| 启动打包产物 | 窗口标题 `Shellune`，客户区 1680×1080 物理像素，DPI 144，stderr 为空 |
| Ctrl+3 / Ctrl+1（切换目的地） | 每次 115,139 像素变化；鼠标点击同一导航项一致（T2 已记录） |
| Ctrl+L（中英切换） | 22,650 像素变化，产品名与英文简介保持不变 |
| Ctrl+=（文字大小） | 100%→115% 162,257；115%→90% 213,968；90%→100% 115,849 |
| 点击"文字大小"控件 | 与快捷键相同的三档循环（204,062 / 113,011 像素） |
| 本地 Shell 执行 `cd C:\Users; pwd` | 输出 `C:\Users`，与本机执行一致 |
| 窗口 1680×1080 → 1350×900 → 复原 | Shell 内 `$Host.UI.RawUI.WindowSize` 从 95×21 → 66×12 → 95×21 |
| 输入 `echo 中文输入测试 > r8-zh.txt` | 文件内容为 `中文输入测试`（UTF-16LE），字符未损坏 |

窗口尺寸变化传到 PTY 的实测数字（95×21 ↔ 66×12）说明 resize 链路是通的，这比 T2 的
纯布局断言更接近 R8 的"调整窗口尺寸后光标与内容区域随之更新"。

### 6.4 本轮发现、未修正的问题：Ctrl+C 不能中断前台命令

在打包产物里：

1. 在 PowerShell 中执行 `ping -n 20 127.0.0.1` 或 `cmd /c ping -n 20 127.0.0.1`，
   等 3 秒后按 Ctrl+C。
2. 观测：界面持续变化（28,396 像素/秒；按 Ctrl+C 后仍有 23,983 像素/秒），提示符
   2.5 秒内没有回来，之后键入的命令要等命令自己结束才执行。
3. 同一台机器的 Windows Terminal 里跑同样的 `cmd /c ping -n 20 127.0.0.1`，
   Ctrl+C 后 3 秒内提示符恢复（用"再执行一条写文件的命令并检查文件"验证）。

字节级追踪（临时 `eprintln`，已回退）显示按键确实被处理并写出：
`key "c" ctrl=true` → `write [3]`；同一路径下 `ctrl+a` → `write [1]`、
`tab` → `write [9]`、`up` → `write [27,91,65]`。
同一台机器上，用 `portable-pty` 写的最小复现程序向 `cmd /c ping` 写入 `0x03` 能中断它。

因此应用侧的编码与写入没有丢字节，问题出在 ConPTY 把该字节转成控制事件的那一步：
PowerShell 作为前台 Shell 时没有发生（PSReadLine 把控制台输入置于不处理控制键的
模式）。它是真实缺陷，不是"平台不支持"——同机同命令在 Windows Terminal 上正常。
本轮既没有把 `0x03` 换成控制台控制事件（需要 `AttachConsole` /
`GenerateConsoleCtrlEvent`，会牵动应用自身的控制台），也没有把结论改成"已验证"。
R8 的"执行持续输出命令后能够中断"因此仍未满足，已写入
`docs/release/0.1.0-verification.md` 与发布说明的已知问题。

### 6.5 本轮仍未覆盖

- 真实中文输入法：字符是通过 Unicode 文本事件送入的（显示与提交一致），但没有驱动
  Windows 输入法的候选窗与组合过程。
- Vim / tmux / top 的交互式全屏验证：MSYS 的 Vim 能在本地 Shell 里启动，但本轮没有
  拿到可信的全屏结果（没有辅助功能树，也无法校对渲染文本），只有自动化测试里
  PTY 层面的证据。
- macOS 与 Linux：未运行。
